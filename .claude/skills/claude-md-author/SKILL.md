# CLAUDE.md author

Produce a `CLAUDE.md` at the repo root that gives any session what it needs to work in this repo correctly on the first try: how to build and test, where things live, the conventions that aren't obvious from the code, and the corrections learned the hard way. Every line costs context in every session, so it stays under about a page.

## What belongs where

| Put it in | When it is |
|---|---|
| `CLAUDE.md` | Repo conventions, commands, layout, gotchas, recurring corrections. True for most sessions in this repo. |
| A skill | Institutional knowledge that must be applied consistently across repos or needs a procedure (policies, artifact formats, review rules). |
| A linked doc | Long reference material a session needs only sometimes. `CLAUDE.md` gets one line pointing at it and saying when to read it. |
| A hook / CI | Anything that must always hold. `CLAUDE.md` is advisory. |
| The prompt | One-off instructions for this task only. |

## Workflow

1. **Read what's there.** Existing `CLAUDE.md` (and nested ones in subdirectories), `README`, build files (`package.json`, `Makefile`, `pyproject.toml`, `Cargo.toml`, CI config), and the top-level layout. If a `CLAUDE.md` exists, it's human-owned: preserve its content and intent, and propose removals rather than silently dropping lines.
2. **Find the real commands.** Build, test (all and single-test), lint/format, typecheck, run locally. Take them from build files and CI config, and run the cheap ones to confirm they work. Never list a command you haven't seen in the repo or verified.
3. **Collect non-obvious conventions.** Things a competent engineer new to the repo would get wrong: generated files not to edit, where migrations go, naming rules, which package owns what, required env vars (names only, never values).
4. **Collect corrections.** If the user describes a repeated mistake, write it as a direct instruction with the reason: "Don't edit `schema.graphql`; it's generated by `make schema` from `schema/*.ts`."
5. **Write it** using the shape below. Apply `writing-for-agents`: an agent follows this document as instructions. Cut anything the code makes obvious, anything the model already knows (general language advice), and anything used by fewer than one session in five (move to a linked doc).
6. **Report back:** what you added, what you cut or moved (with where), and any commands you couldn't verify.

## Shape

```markdown
# <repo name>

One or two sentences: what this repo is.

## Commands
- Build: `...`
- Test all: `...` · single test: `...`
- Lint/format: `...`
- Typecheck: `...`

## Layout
- `src/api/` - HTTP handlers; one file per resource
- ...

## Conventions
- ...

## Gotchas
- <Direct instruction>. <Why, in a clause.>

## References
- `docs/...`: <what it is>. Read it before <when>.

## Verification
(Owned by `verification-setup`; leave this block in place if it exists.)
```

Drop any section with nothing to say; this file is the one place where "None" sections aren't needed.

## Rules of thumb (and why)

- **Under a page.** Long files dilute the instructions that matter and cost context in every session. When it grows, move reference material to linked docs.
- **Instructions, not descriptions.** "Run `make gen` after editing `proto/`" beats "The proto files are compiled by a generator."
- **Give the reason in a clause.** A reason lets the model generalise to cases the rule didn't name.
- **Verified commands only.** A wrong test command wastes every session that trusts it.
- **No secrets.** Env var names, never values; no internal URLs that shouldn't be in the repo.
- **Add a correction when a mistake repeats, not after the first time.** One-offs belong in the prompt.

## Advisory, not enforced

`CLAUDE.md` is read, not enforced. If a gotcha keeps being violated despite being written down, turn it into a hook with `hook-author`.
